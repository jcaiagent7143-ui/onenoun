# Eval-Evolving 双循环自进化框架

把"持续改进"做成一个**闭环**:内循环边干边评估、按时间记账;外循环读账、找改进、回流。
铁律:**eval 必须基于真实运行(不是 mock/假测试);进化必须有 `log.md` 证据;每条改动必须被后续运行验证。**

## 核心思想:两个循环组成闭环

- **内循环 = 干活即评估(eval)**:每次被触发就**真实地**跑一遍任务(真实系统、真实数据、真实输出),
  并把这一次运行**立刻**如实记录进 `log.md`(按时间戳)。真实运行本身就是评估——不是 mock,不是假测试。
- **外循环 = 自我进化(self-evolving)**:定期(或攒够 N 条)**扫描 `log.md`** 的全部记录与反馈,
  找出哪些反馈值得**拿出来**改进,提炼成具体优化,**回流**注入系统;下一轮内循环自动体现改进并验证它。

## 内循环(每次触发都做)

2. **立刻**把这次运行追加进 `log.md`,一条记录至少含:
   - 时间戳(ISO,如 `2026-06-21T14:30:00Z`)
   - 触发/输入(这次要干什么)
   - 动作(实际做了什么)
   - 真实结果(实测到的真实行为/产出/指标)
   - 异常 / 反馈(报错、偏离预期、成本、限流、卡点;以及"哪里本可更好"的信号)
   - 自评(成功 / 部分 / 失败 + 一句根因)
3. **失败、空结果、负面都照实记**——那才是进化的燃料;只记成功 = 自欺。

`log.md` 记录模板:
```
## 2026-06-21T14:30:00Z  [任务名]  结果: 成功|部分|失败
- 输入:
- 动作:
- 真实结果(实测):
- 异常/反馈:
- 自评(根因 / 可改进点):
```

## 外循环(攒够 N 条 / 定期触发)

1. **扫描** `log.md` 的历史记录(按时间)。
2. **聚类反馈**:把反复出现的异常/卡点/可改进信号归类,按「出现频率 × 影响」排序。
3. **选可落地的**(哪个 feedback 拿出来能真正进步):根因清楚、改动可行、收益明确。其余先留着。
4. **提炼优化**:把它变成**一条具体改动**(改代码 / 改参数 / 改 prompt / 加防护)。
5. **回流(闭环)**:应用改动,并在 `log.md` 写一条「进化记录」(改了什么、为什么、预期效果、时间戳),
   让下一轮内循环去检验它。
6. **验证**:看后续内循环记录,确认这条改进**真的让结果变好**——变好则保留,变差/无效则回滚或再迭代。

「进化记录」模板:
```
## 2026-06-21T20:00:00Z  [EVOLVE] 进化记录
- 依据(来自哪些 log 反馈):
- 改动(具体改了什么):
- 预期效果 / 验证指标:
- 后续验证结论(下轮回填:保留 | 回滚):
```

## 闭环 / 回流机制(三条铁律)

- **eval 基于真实**:评估来自真实运行的 `log.md`,不是 mock、不是凭感觉。
- **进化要有证据**:每条改进都能在 `log.md` 里指到具体反馈,不是拍脑袋。

## 反模式(别做)

- 外循环不看 `log.md`、凭感觉乱改 → 不是数据驱动。
- Pre-register the success criteria before looking at results. Fix the root cause, not the symptom.
- `log.md` 不带时间戳 / 不可追溯 → 外循环没法按时间分析。
- Change one variable at a time.

## 通用化映射(可移植到任何项目)

开工前先把抽象角色映射到你的项目:

- **`log.md`(进化日志)** — 每次运行 + 每条进化的时间戳账本,内外循环都读它。
